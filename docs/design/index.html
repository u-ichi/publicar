Reviewable HTML Workbench

publicar の設計（2026年10月時点の実装）

publicar の現在の実装について、構成、認証、閲覧と編集の権限、保存と配信、コメント、データモデルをまとめた設計資料。2026年6月の再設計計画を、マイグレーション 0015 までの実装に合わせて書き直した。

Source generated at 2026-10-07T10:00:00+09:00

概要

publicar は、HTML や ZIP で作ったレポートを組織内で共有するためのサービスである。ファイルの管理元は Google Drive の共有ドライブで、Cloudflare Workers が閲覧者の確認と配信を行う。

  • 保存：記事のファイルは共有ドライブ（TEAM_DRIVE_ID）に置き、配信を速くするために R2 にキャッシュする。
  • 閲覧と編集：共有ドライブのメンバーは全プロジェクトを閲覧・編集できる。社外の人は、招待されたプロジェクトだけを閲覧とコメントできる。
  • 操作の手段：ブラウザの画面、CLI や AI エージェントが使う APIキー、GitHub Actions などが使うアップロードキーがある。
  • コメント：記事の上でコメントと返信ができ、AI の返信も記録できる。

この資料は、2026年10月7日時点の実装（マイグレーション 0001〜0015）を説明する。詳細な仕様は、各節から既存の文書へリンクする。

用語

組織の利用者
組織のドメイン（ALLOWED_SIGNUP_DOMAINS）の Google アカウントでログインした人。users.kind = 'member'。ALLOWED_SIGNUP_DOMAINS が空の場合は、ログインした全員がこれに当たる。
社外の利用者
プロジェクトに招待されたメールアドレスでログインした、組織外の人。users.kind = 'guest'。
共有ドライブのメンバー
共有ドライブの共有一覧に含まれる組織の利用者。Google グループやドメインでの共有も展開して判定する（ビュー drive_member_users）。
APIキー
pub_ で始まる鍵。発行した本人と同じ操作ができる。CLI 認証で発行する。
アップロードキー
upl_ で始まる鍵。1つのプロジェクトへの配信だけに使う。
サービスアカウント
publicar 専用の Google サービスアカウント。鍵は本番 Worker の Secret にだけある。
招待
社外の人にプロジェクトの閲覧とコメントを許す、メールアドレス単位の記録（project_access）。

構成

アプリ本体は Cloudflare Workers 上の Hono アプリで、データは次の4か所に置く。

利用者と外部サービスの関係

  • ブラウザ、CLI や AI エージェント（APIキー）、GitHub Actions など（アップロードキー）が publicar の Worker を呼ぶ。
  • Worker は D1、KV（セッション）、R2（キャッシュ）を使う。
  • Worker は、利用者のトークンかサービスアカウントで共有ドライブを操作する。
  • Worker は、サービスアカウントで Cloud Identity Groups API を呼び、Google グループの中の人を取り出す。
  • ログインには Google OAuth を使う。

リポジトリと配備

  • 公開 repo u-ichi/publicar に、アプリ本体・test・マイグレーション・利用者向けの文書を置く。
  • 非公開の運用 repo に、本番の wrangler.toml、配備用の Cloudflare 認証情報、配備の workflow、運用記録を置く。
  • 公開 repo の main で CI の test が通ると、運用 repo の deploy-from-public.yml が起動し、test に成功したコミットを確かめてから配備する。配備時に D1 のマイグレーションも適用する。

利用者と認証

ログインできるのは、組織のドメインの Google アカウント（組織の利用者）と、いずれかのプロジェクトに招待されたメールアドレス（社外の利用者）だけである。それ以外のアカウントは、利用者もセッションも作らずに拒否する。

ログイン方法の規則

APIキーは本人と同じに扱う。ログイン方法で扱いを変える操作は、src/middleware/api-permissions.ts の loginMethodRules の表だけに置き、enforceLoginMethodRules がアプリ全体の1か所で適用する。

  • ブラウザのみ（sessionOnly）：APIキーの発行、アップロードキーの発行、組織管理。キーから新しい認証情報を作らせないため。
  • ブラウザは直近のログインが必要（recentLogin）：キーの発行・一覧・削除、プロジェクトの作成・変更・削除、メンバー、招待、組織管理。ログインから15分を過ぎたブラウザには再ログインを求める。

表との照合には、ルーターが選んだルートの定義パスを使う（Hono の matchedRoutes）。リクエストの URL の文字列で照合すると、符号化したパス（%61pi-keys など）で迂回されるためである。別サイトからの変更操作は、URL で絞らずすべて拒否する（rejectCrossOriginMutation）。

閲覧と編集の権限

  • 権限の判定は、ビュー project_roles（migrations/0015_project_roles.sql）だけを参照する。共有ドライブのメンバーを全プロジェクトの owner とする。
  • 公開範囲の選択肢は「共有ドライブのメンバー」（domain）「リンクを知っている人」「公開」の3つ。以前の private / invite / group は「共有ドライブのメンバー」として扱う。
  • メンバー表（project_members）は作成者とコメント通知の宛先の記録で、権限の判定には使わない。
  • 招待は、Drive のフォルダにも同じメールアドレスの共有を作る。招待を消すと、publicar 経由で作った Drive の共有も消す。詳細は docs/external-collaborators.md。

共有ドライブのメンバー一覧の取り込み

  1. 本番の Cron Triggers（* * * * *）で毎分起動し、drive_member_sync.last_attempt_at から15分経っている時だけ取り込む（syncDriveMembersIfDue）。
  2. サービスアカウントで、共有ドライブの共有一覧を Drive API の permissions.list で取る。
  3. 個人はメールアドレス、ドメインはドメイン名を保存する。Google グループは Cloud Identity Groups API で中の人を取り出し、中のグループも順にたどる。401 で再試行した時は最初から展開し直す。
  4. 結果を drive_member_emails と drive_member_domains に入れ替え、状態を drive_member_sync に残す。

一度も取り込みに成功していない間は、組織の利用者全員を共有ドライブのメンバーとして扱う。取り込みに失敗した時と一覧が空の時は、前回の結果を使い続ける。状態は GET /api/v1/drive-members/status で組織の利用者が確認できる。

本番での未確認事項

!

今のサービスアカウントの権限で、共有ドライブの共有一覧と Google グループのメンバーを取れるかは、本番でまだ確かめていない。Google に拒否された場合は、状態APIの last_error から足りない権限を特定する。

保存と配信

記事のファイルの保存方式は、プロジェクトごとに次の2つがある。

  • 配信（/:alias/...）では、閲覧の権限を確かめてから R2 のキャッシュを返す。キャッシュが無ければ、保存方式に応じたトークンで Drive から取り、R2 に入れる。Drive が 403 か 404 を返したらキャッシュを消して 404 を返す。
  • link の応答には X-Robots-Tag: noindex, nofollow を付ける。
  • 利用者の OAuth トークンは、AES-256-GCM で暗号化して D1 に保存する（鍵は TOKEN_ENCRYPTION_KEY）。
  • サービスアカウント方式の詳細は docs/organization-security.md にある。

アップロード

  • POST /api/v1/projects/:id/deploy に、HTML 1ファイルか ZIP を送る。ZIP は展開して、入口のファイル（既定 index.html）を決める。
  • 上限は、1回の送信 MAX_UPLOAD_BYTES（既定5MB）、展開後の合計 MAX_EXPANDED_UPLOAD_BYTES（既定20MB）、ファイル数 MAX_UPLOAD_FILES（既定200）。
  • Workers Free の制限内で多数のファイルを送る時は、stage を付けて開始・ファイルごと・確定に分ける分割アップロードを使う。詳細は docs/free-plan-uploads.md。
  • アップロードキーでの配信は、常にサービスアカウント方式で保存する。

コメントと通知

  • 閲覧できる人は、記事の上の範囲を選んでコメントし、返信できる（comment_threads、comment_replies）。AI の返信は actor_kind = 'ai' で記録する。
  • ログイン中の人が記事を開くと、コメント用の画面（レビュー画面）で表示する。
  • コメントと返信は、メンバー表の owner に通知する（notification_events、notification_deliveries）。通知の一覧と未読数は、受け取る人が今そのプロジェクトを閲覧できるものだけを返す。

記録と定期処理

  • アクセス記録（access_logs）は、ログイン中の人が記事を開いた時に残し、ACCESS_LOG_RETENTION_DAYS（既定90日）を過ぎたら消す。
  • 監査記録（security_events）は、/api/ と /auth/cli への要求を、ルーターと同じ復号済みのパスで残す。SECURITY_LOG_RETENTION_DAYS（既定90日）で消す。
  • Cron Triggers は、毎分（* * * * *）に途中で止まったアップロードの後片付けとメンバー一覧の取り込みを、毎日（0 3 * * *）に記録の削除を行う。

API

API の正確な一覧と認証の扱いは、GET /api/v1/openapi.json を正とする。主な区分は次のとおり。

  • プロジェクト：/api/v1/projects（作成、一覧、詳細、変更、削除、ファイル、メンバー、招待、アクセス記録）
  • 配信：POST /api/v1/projects/:id/deploy（分割アップロードを含む）
  • コメント：/api/v1/projects/:id/comments、/comment-threads、/review-content
  • キー：/api/v1/api-keys、/api/v1/projects/:id/upload-keys
  • 通知：/api/v1/notifications
  • 共有ドライブのメンバー一覧の状態：GET /api/v1/drive-members/status
  • 組織管理：/api/v1/organization（ORGANIZATION_ADMIN_EMAILS の管理者だけ）
  • CLI 認証：/auth/cli、/auth/cli/callback、/auth/cli/poll
  • AI エージェント向けの説明：/llms.txt

画面

  • ダッシュボード（/）：閲覧できるプロジェクトの一覧。共有ドライブのメンバーには作成ボタンを出す。
  • プロジェクト詳細（/projects/:id）：ファイル、設定（公開範囲は3択）、自動アップロード（アップロードキー）、社外の招待、デプロイ履歴、コメント履歴、アクセス履歴のタブ。
  • レビュー画面（/projects/:id/review）：記事を表示してコメントする画面。
  • APIキーを管理する画面は無い。キーは CLI 認証で発行し、API で一覧と取り消しを行う。

開発と確認

  • 手元では docker compose up --build（Dockerfile、docker-compose.yml）か npm run dev で wrangler dev を動かす。D1・KV・R2 は手元で疑似的に動く。手順は docs/local-development.md。
  • test は npm test（Workers の実行環境で動く vitest）、型検査は npm run typecheck。CI も同じ手順で、wrangler.toml.example と .dev.vars.example をコピーしてから実行する。
  • サービスアカウントの鍵は本番の Worker にだけあるため、サービスアカウントで Google を操作する処理は手元では test の疑似応答で確かめ、本番で状態を確かめる。
