Reviewable HTML Workbench

publicar 再設計: SSSS 相当の OSS AI レポート共有基盤

Source generated at 2026-06-15T00:00:00Z

概要

i

publicar を Cloudflare Access + R2 の社内 HTML ホスティングから、SSSS (SuperSonic Sharing Service) 相当の「AI 生成レポート共有基盤」に再設計し、OSS として公開する。ストレージを Google Drive に切り替え、柔軟なアクセス制御と AI エージェント連携 API を追加する。

ゴール

publicar の再設計で達成する 4 つの目標を定義する。

  • セルフホスト可能: 誰でも wrangler deploy 一つで自分の publicar インスタンスを立てられる
  • AI エージェント連携: Claude Code, ChatGPT 等が /llms.txt で API を自己発見し、HTML/ZIP をアップロードして共有 URL を取得できる
  • Google Drive 保存: アップロードしたファイルはユーザー自身の Google Drive に保存され、publicar 側は配信キャッシュ (R2) のみ保持する
  • 柔軟なアクセス制御: ページごとに公開範囲 (private / invite / domain / link / public) を設定できる

設計方針（決定済み）

以下の技術選定は確定済みであり、各フェーズの実装はこれらの方針に従う。

項目決定理由
ストレージGoogle Drive（管理元）+ R2（配信キャッシュ）ユーザーがファイル所有権を持ち、Drive 権限取消で即停止。R2 でエッジ配信の低レイテンシ維持
閲覧者認証Google OAuthDrive 連携に Google OAuth が必然。visibility に応じて email / ドメインでアクセス判定
API 認証API キー (pub_...)AI エージェント等がステートレスに操作可能。セッション不要
実行環境Cloudflare Workers 固定Hono + Workers のまま。wrangler deploy で簡単にデプロイ可能
メタデータD1 (SQLite)SQL クエリ対応。スキーマ定義・マイグレーションが標準的。無料枠 5GB
セッションKV低レイテンシ (1-10ms)。TTL による自動削除
公開形態OSS (GitHub public repo)SSSS の代替としてコミュニティ利用を想定
テナントモデルシングルテナント組織モード: 1 インスタンス = 1 組織（Shared Drive が 1 つのため）。個人モード: 1 インスタンスを複数ユーザーで共有可能（各自の Drive を使用）。組織をまたぐマルチテナントには非対応

データフロー: アップロード

  1. 認証（セッション Cookie or API キー Bearer pub_...）
  2. ファイルを Google Drive（ユーザーの「publicar」フォルダ）に保存
  3. 同じファイルを R2 にキャッシュとして書き込み
  4. D1 にメタデータ（alias, visibility, drive_file_id, r2_key 等）を記録
  5. {alias, url} を返却

データフロー: 配信

  1. alias から D1 でプロジェクト取得 → visibility チェック
  2. R2 キャッシュ確認 → ヒットなら即配信
  3. ミスなら → オーナーの OAuth トークンで Drive API から取得 → R2 にキャッシュ → 配信
  4. Drive API が 403/404 → R2 キャッシュ削除 + 404 返却（権限取消対応）

データモデル概要

publicar が扱う主要な概念と、それらの関係を定義する。

前提: 組織モード（TEAM_DRIVE_ID 設定時）では 1 インスタンス = 1 組織。Shared Drive が 1 つに固定されるため、複数組織の混在はできない。個人モード（TEAM_DRIVE_ID 未設定）では 1 インスタンスを複数ユーザーで共有可能。各ユーザーが自分の Drive にファイルを保存するため、互いに干渉しない。

エンティティ定義

概念定義ライフサイクル
UserGoogle OAuth でログインしたアカウント。email で一意に識別される。初回ログイン時に自動作成（登録制御の条件を満たす場合のみ）。
Project1 つの公開 URL (/p/:alias) に対応するファイル群の単位。title, alias, visibility, entry_path を持つ。alias は URL 用識別子で、title から自動決定されるかユーザーが明示指定する。POST /api/v1/deploy で新規作成。同じ alias への再 deploy で上書き更新。DELETE /api/v1/projects/:id で削除。
ProjectMemberProject と User の関連。role（owner / editor / viewer）を持つ。1 Project に複数の owner を設定可能。Project 作成時に作成者を owner として自動登録。owner がメンバー追加・削除・role 変更できる。
FileProject に属する個別ファイル（HTML, CSS, JS, 画像等）。project_id + path で一意。deploy 時に作成・上書き。Project 削除時に CASCADE 削除。
ProjectAccessvisibility が invite の Project に対するメール単位の閲覧許可。未登録ユーザーへの招待にも使える。owner が追加・削除。Project 削除時に CASCADE 削除。
API KeyUser に紐づく認証トークン。AI エージェント等がセッションなしで API を呼ぶために使う。User が発行・削除。

アカウント登録制御

誰がインスタンスにアカウントを作成できるかは、環境変数の組み合わせで決まる。

環境変数登録できるユーザー想定用途
どちらも未設定最初にログインした 1 人のみ（以降は招待制）個人利用
ALLOWED_SIGNUP_DOMAINS のみ指定ドメインのメールアドレスを持つユーザー組織利用（Shared Drive なし）
TEAM_DRIVE_ID + ALLOWED_SIGNUP_DOMAINS指定ドメインのユーザー + Shared Drive にファイル集約組織利用（推奨構成）

招待制の仕組み: 既存ユーザー（owner ロール）が POST /api/v1/invites でメールアドレスを指定して招待。招待されたユーザーは Google OAuth ログイン時に自動登録される。招待なしのログインは 403。

閲覧権限と編集権限

publicar では閲覧権限と編集権限を別の仕組みで管理する。

制御する仕組み対象
閲覧visibility（projects テーブル）コンテンツを /p/:alias で見られるか
編集project_members テーブルファイルの deploy・上書き・プロジェクト設定変更ができるか

例（組織モード、visibility: domain）:

  • 同一ドメインの全員 → 閲覧可能（member でなくても見える）
  • project_members に登録された owner / editor → 編集・deploy 可能
  • project_members の viewer → visibility に関係なく閲覧可能（invite や private でも見える）

運用モード

publicar は 組織モード と 個人モード の 2 つの運用形態をサポートする。環境変数 TEAM_DRIVE_ID の有無で切り替わる。

組織モード (TEAM_DRIVE_ID 設定あり)個人モード (TEAM_DRIVE_ID 未設定)
ストレージ組織の Google Shared Drive (Team Drive) に全ファイルを保存deploy した User の個人 Drive (マイドライブ) に保存
ファイルの所有Shared Drive が所有。個人に紐づかないdeploy した User が所有
引き継ぎ・修正同じ Shared Drive にアクセスできるメンバーなら誰でも上書き・削除可能owner / editor のみ操作可能。Drive トークンは deploy した User のものが必要
退職・異動時ファイルは Shared Drive に残る。User を削除しても影響なしUser の Drive アカウントが無効化されると配信停止
認証制限ALLOWED_SIGNUP_DOMAINS との併用を推奨任意

deploy の動作

POST /api/v1/projects/:id/deploy は既存プロジェクトへのファイルアップロード専用。プロジェクト作成は POST /api/v1/projects で行う。

条件動作
プロジェクトが存在 + 実行者が owner/editorファイルをアップロード（上書き更新）
プロジェクトが存在 + 権限なし403 Forbidden
プロジェクトが存在しない404 Not Found

上書き時の挙動: 新しいファイルで既存ファイルを置換する。ZIP deploy の場合、ZIP に含まれないファイルは削除される（クリーンデプロイ）。

D1 スキーマ: SQL 定義

CREATE TABLE users (
  id TEXT PRIMARY KEY,
  google_id TEXT NOT NULL UNIQUE,
  email TEXT NOT NULL UNIQUE,
  name TEXT,
  avatar_url TEXT,
  encrypted_access_token TEXT,
  encrypted_refresh_token TEXT,
  token_expires_at INTEGER,
  drive_folder_id TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE projects (
  id TEXT PRIMARY KEY,
  alias TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  description TEXT,
  created_by TEXT NOT NULL REFERENCES users(id),
  visibility TEXT NOT NULL DEFAULT 'private'
    CHECK (visibility IN ('private','invite','domain','group','link','public')),
  allowed_domains TEXT DEFAULT '[]',
  allowed_groups TEXT DEFAULT '[]',
  entry_path TEXT DEFAULT 'index.html',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE project_members (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role TEXT NOT NULL DEFAULT 'viewer'
    CHECK (role IN ('owner','editor','viewer')),
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE (project_id, user_id)
);

CREATE TABLE project_files (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  path TEXT NOT NULL,
  drive_file_id TEXT,
  r2_key TEXT NOT NULL,
  size_bytes INTEGER,
  content_hash TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE (project_id, path)
);

CREATE TABLE project_access (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  email TEXT NOT NULL,
  granted_by TEXT NOT NULL REFERENCES users(id),
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE (project_id, email)
);

CREATE TABLE api_keys (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  key_prefix TEXT NOT NULL,
  key_hash TEXT NOT NULL UNIQUE,
  scopes TEXT NOT NULL DEFAULT '["read","write","deploy"]',
  last_used_at TEXT,
  expires_at TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE invites (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL,
  invited_by TEXT NOT NULL REFERENCES users(id),
  used_at TEXT,
  expires_at TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE (email)
);

認証設計: API キー

項目仕様
形式pub_<base62(32bytes)> (約 43 文字)
保存SHA-256 ハッシュのみ D1 に保存。平文は発行時の一度だけ返却
検証Authorization: Bearer pub_... → SHA-256 → D1 lookup
スコープread / write / deploy

認証設計: 統合認証ミドルウェア

リクエスト受信
  → Bearer pub_... ? → API キー検証 → user_id 解決
  → publicar_session cookie ? → KV セッション取得 → user_id 解決
  → どちらもない → 401 (API) or 302 /auth/login (ブラウザ)

セキュリティ: トークン暗号化

i

OAuth トークンは crypto.subtle の AES-256-GCM で暗号化して D1 に保存。暗号化キーは環境変数 TOKEN_ENCRYPTION_KEY (wrangler secret)。IV は毎回ランダム生成し暗号文の先頭 12 bytes に付加。

API 設計: デプロイ（ファイルアップロード）

既存プロジェクトに対してファイルをアップロードする。プロジェクトは事前に POST /api/v1/projects で作成しておく。

メソッドパスContent-Typeパラメータレスポンス
POST/api/v1/projects/:id/deploy?path=index.htmlapplication/octet-streambody = ファイルバイナリ{ok, url}
POST/api/v1/projects/:id/deploy?name=site.zipapplication/octet-streambody = ZIP バイナリ{ok, files, entry, url}

ZIP と単一ファイルを分ける理由: 単一 HTML は AI エージェントがレポート 1 枚を即共有する最もシンプルなケース。ZIP は CSS/JS/画像を含むマルチファイルサイト用で、サーバー側で fflate により展開して全ファイルを配置する。

entry_path の決定ロジック（ZIP deploy 時）:

  1. ZIP 内に index.html があればそれを entry_path に設定
  2. なければ、ZIP ルートの .html ファイルが 1 つだけならそれを採用
  3. 複数あれば最初の .html を採用。entry_path は PATCH /api/v1/projects/:id で後から変更可能

上書き時の挙動: 新しいファイルで既存ファイルを置換する。ZIP deploy の場合、ZIP に含まれないファイルは削除される（クリーンデプロイ）。

使用例（AI エージェントの典型的なフロー）:

# 1. プロジェクト作成
curl -X POST "$BASE/api/v1/projects" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"title": "月次レポート", "visibility": "domain"}'
# → {"ok":true, "id":"proj_xxx", "alias":"monthly-report"}

# 2. ファイルをデプロイ
curl -X POST "$BASE/api/v1/projects/proj_xxx/deploy?path=index.html" \
  -H "Authorization: Bearer $KEY" \
  --data-binary @report.html
# → {"ok":true, "url":"https://publicar.example.com/p/monthly-report"}

# 同じプロジェクトへの再デプロイ（上書き更新）
curl -X POST "$BASE/api/v1/projects/proj_xxx/deploy?name=report.zip" \
  -H "Authorization: Bearer $KEY" \
  --data-binary @report.zip
# → {"ok":true, "files":5, "entry":"index.html", "url":"https://publicar.example.com/p/monthly-report"}

プロジェクト作成時のレスポンス:

{"ok": true, "id": "proj_xxx", "alias": "monthly-report", "url": "https://.../p/monthly-report"}

alias の決定ロジック:

  1. alias を明示指定 → その値を使用
  2. alias 未指定 + title が ASCII のみ（英数字・ハイフン・アンダースコア） → title を小文字化・スペースをハイフンに変換して alias にする（例: Monthly Report → monthly-report）
  3. alias 未指定 + title に日本語等の非 ASCII 文字を含む → ランダム alias を自動生成（例: rpt-a3f8k2）

alias は [a-z0-9][a-z0-9-]* の形式に制限。重複時はサフィックス（-2, -3）を付与。作成者は自動的に owner として project_members に登録される。

アクセス制御: オーナー・メンバー権限

Google OAuth でログインし、コンテンツをアップロード・管理する側の権限モデル。

組織での利用

組織で publicar を運用する場合、以下の 3 つの環境変数を設定する。

環境変数役割例
ALLOWED_SIGNUP_DOMAINSログイン可能なメールドメインを制限example.com,example.co.jp
TEAM_DRIVE_IDファイル保存先の Shared Drive ID0ABcDeFgHiJkLmN
DEFAULT_VISIBILITY新規プロジェクトのデフォルト公開範囲domain（組織内公開）

この組み合わせにより:

  • 組織ドメインのユーザーのみログイン可能
  • アップロードしたファイルは組織の Shared Drive に集約
  • デフォルトで同じドメインのユーザーが閲覧可能
  • 他のメンバーがアップロードしたファイルも引き継ぎ・修正可能（Shared Drive の特性）

個人での利用

上記の環境変数を設定しなければ個人モードで動作する。

  • 最初にログインしたユーザーのみ自動登録。以降は招待制
  • ファイルは各ユーザーの個人 Drive に保存
  • 新規プロジェクトは private（自分だけ閲覧可能）

Shared Drive の前提条件

  • Google Workspace の Shared Drive 機能が有効であること（個人 Google アカウントでは利用不可）
  • publicar を利用するユーザーが Shared Drive のメンバーであること
  • OAuth スコープ drive.file で、アプリが作成したファイルへのアクセスが可能

アクセス制御 (b): 閲覧者の Visibility モデル

閲覧者（コンテンツを見る側）のアクセス制御。プロジェクトごとに設定する。

visibility閲覧条件認証
privateオーナー本人のみ必須（セッション or API キー）
inviteproject_access に email 登録済みユーザー必須（Google ログインで email 確認）
domainallowed_domains に email ドメインが一致必須（Google ログインでドメイン確認）
linkURL を知っていれば誰でも不要（noindex 付与）
public完全公開不要
group（バックログ）Google Group のメンバーのみ閲覧可能。allowed_groups に Google Group メールアドレスを指定必須（Google ログイン + Groups API）

バックログ: Google Group 対応

visibility: group は初期実装には含めない。ただし以下の設計上の考慮を入れておく:

  • D1 スキーマ: projects.allowed_groups カラム（JSON 配列）を初期マイグレーションに含める（空配列のまま未使用）
  • visibility の CHECK 制約に group を含めておく
  • UI: visibility セレクトボックスに group を disabled 状態で表示（「近日対応」のラベル付き）
  • 実装時に必要: Cloud Identity Groups API or Directory API、追加 OAuth スコープ、グループメンバーシップのキャッシュ層

GUI デザイン要求仕様

publicar の Web UI はシンプルな管理画面として設計する。主な利用者は組織内のレポート作成者（AI エージェント経由が主）と、レポートの閲覧者。UI は最小限で、主要操作は API 経由を前提とする。

デザイン原則

  • ダークテーマ基調: 背景 #0a0a0a〜#1a1a1a、文字 #e0e0e0。開発者・技術者向けツールとしてのトーン
  • レスポンシブ: デスクトップ優先だがモバイルでも閲覧可能
  • フレームワーク不使用: Vanilla HTML/CSS/JS。Workers で配信するため軽量に保つ
  • 日本語 UI: ラベル・メッセージは日本語。技術用語（alias, visibility 等）は原語のまま

  6. OSS としての最小構成（必要な設定、ドキュメント）は十分か

Claude Design 用プロンプト

以下をそのまま Claude Design に貼り付けて使用する。

publicar — AI 生成レポート共有基盤の Web UI をデザインしてください。

## サービス概要
組織内で AI エージェントが生成した HTML レポートを共有するための Cloudflare Workers ベースのホスティングサービス。組織の Google Shared Drive にファイルを保存し、ドメイン単位でアクセス制御する。

## デザイン原則
- ダークテーマ基調（背景 #0a0a0a〜#1a1a1a、文字 #e0e0e0）
- 開発者・技術者向けのクリーンで落ち着いたトーン
- フレームワーク不使用を前提としたシンプルな構造
- 日本語 UI（技術用語 alias, visibility 等は原語のまま）
- レスポンシブ（デスクトップ優先）

## カラーパレット
- 背景メイン: #0a0a0a
- 背景カード・入力欄: #1a1a1a
- 背景ホバー: #2a2a2a
- ボーダー: #333333
- テキスト主: #e0e0e0
- テキスト副: #888888
- アクセント: #3b82f6（青）
- 危険操作: #ef4444（赤）
- 成功: #22c55e（緑）

## タイポグラフィ
- 本文: system-ui, -apple-system, sans-serif
- コード・alias: ui-monospace, monospace
- ロゴ「publicar」: ui-monospace、太字、レタースペーシング広め、白文字

## デザインする画面（5 画面）

### 1. ログイン画面（パス: / 未認証時）
- 中央配置のカード型レイアウト
- publicar テキストロゴ（モノスペース太字、白）
- 「AI 生成レポート共有基盤」の 1 行説明
- 「Google でログイン」ボタン（Google ブランドガイドライン準拠の見た目）
- カード下部に「@example.com のアカウントでログインしてください」のドメイン案内テキスト（副テキスト色）

### 2. ダッシュボード（パス: / 認証済み）
- ヘッダー: 左に publicar ロゴ、右にユーザーアバター（丸）+ メールアドレス + ログアウトリンク
- メインエリア: プロジェクトカードのグリッド（2〜3 列）
- 各カードの内容:
  - プロジェクト名（リンク）
  - alias 表示（モノスペース、/p/my-report のような形式。alias は URL 用識別子で、title が英数字のみなら title から自動生成、日本語を含む場合はランダム生成。ユーザーが明示指定も可能）
  - visibility バッジ（色分け: private=赤, invite=橙, domain=青, link=緑, public=グレー）
  - 自分の role バッジ（owner / editor / viewer）
  - 最終更新の相対時間（「3 時間前」）
  - 作成者（アバター小 + 名前、例:「田中太郎」）
  - ファイル数
- ヘッダー下に検索バー + 「新規プロジェクト」ボタン（青）
- サンプルデータ: 6 件のプロジェクトカードを表示。visibility と role はバラけさせる

### 3. プロジェクト詳細画面（パス: /projects/:id）
- ヘッダーはダッシュボードと共通
- パンくずリスト: ダッシュボード > プロジェクト名
- タブ切替 UI（下線スタイル）: ファイル | 設定 | メンバー | デプロイ履歴
- 「ファイル」タブ（デフォルト表示）:
  - ファイルツリー表示（インデント付きリスト）
  - 各行: ファイル名、サイズ、更新日時
  - 上部に「ファイルをアップロード」「ZIP をアップロード」ボタン
  - サンプル: index.html, styles/main.css, assets/chart.png 等 5〜6 ファイル
- 「メンバー」タブの内容も別途デザイン:
  - メンバー一覧テーブル: アバター、メール、role（セレクトボックス）、追加日、削除ボタン
  - 「メンバーを追加」フォーム: メールアドレス入力 + role セレクト + 追加ボタン

### 4. API キー管理画面（パス: /settings/api-keys）
- ヘッダー共通
- 既存キー一覧テーブル: 名前、プレフィックス（pub_xxxxxxxx...）、スコープバッジ（read/write/deploy）、最終使用日時、削除ボタン（赤）
- 「新しい API キーを発行」ボタン（青）
- 発行後のモーダルダイアログ:
  - 「API キーが発行されました」タイトル
  - フルキー表示エリア（モノスペース、背景 #1a1a1a、ボーダー付き）
  - 「コピー」ボタン
  - ⚠️ 警告テキスト「このキーは再表示できません。安全な場所に保存してください」
  - 「閉じる」ボタン

### 5. コンテンツ配信画面（パス: /p/:alias、管理者ログイン中）
- 画面最上部に薄い管理者バー（高さ 32px 程度、背景 #1a1a1a、ボーダー下線）
  - 左: プロジェクト名（リンク）
  - 中央: visibility バッジ（domain）
  - 右:「編集」リンク（プロジェクト詳細へ）
- バー以下はアップロードされた HTML コンテンツがフル幅で表示される想定（プレースホルダーでよい）

## 共通コンポーネント仕様
- ボタン: 角丸 6px、パディング 8px 16px。primary=青背景白文字、secondary=透明+ボーダー、danger=赤背景
- カード: 角丸 8px、ボーダー #333、ホバーでボーダーが少し明るくなる
- バッジ: 小さい角丸ラベル、背景色で種類を区別、フォントサイズ小さめ
- ダイアログ: 中央モーダル、背景オーバーレイ rgba(0,0,0,0.7)
- トースト通知: 右下に一時表示、成功=緑枠、エラー=赤枠
