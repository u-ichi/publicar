# Workers Freeで記事を小分けに送信する設計

実装前の設計。Workers Freeで、自動アップロード用キーの発行と、複数ファイルの記事更新を完了できるようにする。
Google Driveを主保存先、R2をファイルキャッシュ、D1を管理情報、KVを認証情報の保存先として使う構成を保つ。
公開URL・閲覧権限・コメント・成功した更新の履歴を保持する。

## 1. 何を分けるか

現在のキー発行は、既存の全Driveファイルを一度のWorker実行で確認する。記事のZIP送信も、全ファイルを一度に展開・保存する。
外部通信が50回を超えると、Freeの制限で失敗する。キー発行の準備、記事の送信、未使用ファイルの削除を、それぞれ少数の処理で応答する方式へ変更する。

| 対象 | 一回で行う処理 | 続きを進める側 |
|---|---|---|
| キー発行の準備 | 保存先と既存ファイル1件の確認、確認済みの位置の保存 | 所有者画面。202応答の後に次のPOSTを行う |
| 記事の送信開始 | ファイル一覧の検証、Drive IDの事前確保、更新の記録 | GitHub Actionsの送信処理 |
| ファイルの送信 | ファイル1件をDriveとR2へ保存 | 同上 |
| 公開の確定 | 全件の完了と現在の認可を確認し、D1で公開版を切り替える | 同上 |
| 未使用ファイルの削除 | ファイルとフォルダを合計5件まで処理 | 定期実行。残りは次回へ回す |

各POSTは実際に処理を進める。固定秒数の待機や、何も処理しない状態確認の繰り返しは追加しない。
従来のZIP一括送信は互換性のため残すが、大きなZIPをFreeで送る経路には分割送信を使う。

## 2. キー発行の準備を続きから進める

`POST /api/v1/projects/{id}/upload-keys` は、従来と同じ `name`、`expires_at` を受け取る。
所有者のセッションだけに許可し、準備が終わるまで秘密キーを発行しない。

1. 保存方式の切替IDを確保する。既存の手動アップロードや削除が実行中なら409を返す。
2. 対象フォルダとサービスアカウントを固定する。新規フォルダは作成用IDを事前に確保し、削除用の追跡行を保存してから作る。
3. 既存ファイルをID順に1件確認する。対象一覧が変わらないよう、準備中は既存の切替制御を維持する。
4. 切替ID・期限・保存先・サービスアカウント・直前の確認位置・現在の所有者権限が一致する場合だけ、確認済みの位置を進める。
5. 残りがあれば `202 {"status":"preparing"}` を返す。所有者画面は同じ入力で次のPOSTを行う。
6. 全件を確認したら、保存方式の有効化と、採用した新規フォルダの削除追跡行の除去を同じD1 transactionで行う。採用した新規フォルダの親と操作識別子はprojectsへ保持し、後のプロジェクト削除時に、現在の所有者を条件とする同じtransactionで削除追跡行へ戻す。その後、現在の所有者権限を再確認してキーを発行し、従来どおり201を返す。

確認済みの位置と準備用フォルダは、同じ切替処理の10分間の有効期限内だけで再利用する。期限が切れたら位置を破棄し、準備用に作ったフォルダも再利用せず、変更後の一覧と新しい作成IDでやり直す。採用の条件付き更新は期限内に限り、削除は作成から一時間経過後に限るため、同じ準備フォルダの採用と削除を同時に成立させない。
一時的な通信失敗では、直前に保存した位置を保持する。保存先や権限の不一致ではキーを発行しない。
画面の通信が途絶えた場合は自動的にキー発行を再送せず、既存どおり発行済み一覧を確認する案内を出す。準備中の再操作は保存した位置から再開する。

## 3. 分割送信API

既存の `POST /api/v1/projects/{id}/deploy` に `stage` を追加する。
アップロード専用キーに許可するURLとHTTPメソッドは広げない。全段階で同じ `Idempotency-Key` を使い、プロジェクト・送信者・要求IDで更新の記録を特定する。

| 要求 | 入力 | 成功応答 |
|---|---|---|
| `POST .../deploy?stage=start` | JSONの `files` 配列 | 新規作成は201、同じ開始要求の再送は200。更新IDと `status: "uploading"` を返す |
| `POST .../deploy?stage=file&path=...` | 一件のファイルの生データ | 200。該当pathの保存成功を返す |
| `POST .../deploy?stage=complete` | 本文なし | 200。従来の複数ファイル更新と同じURL・件数・入口・更新IDを返す |

送信ファイル一覧の要素は `path`、`size_bytes`、`content_hash` のみとする。
`content_hash` は既存のファイル情報と同じ、SHA-256のURL-safe Base64表現（末尾の `=` なし）。
MIMEは既存の拡張子対応から、入口ファイルは既存の `determineEntryPath` から決める。開始後の差替えは許可しない。

入口で次を検証し、外部書込みの前に拒否する。

- JSON本文は解析前に128KiBまでに制限する。余分な項目を受け付けない。
- pathはUTF-8で512byte以内。既存の正規化を適用し、正規化後の重複・絶対path・親への移動・空の要素・backslashを拒否する。
- 件数は既存の `MAX_UPLOAD_FILES`（既定200）、合計サイズは `MAX_EXPANDED_UPLOAD_BYTES`（既定20MiB）以内。
- 一件のサイズは整数かつ0以上、`MAX_UPLOAD_BYTES`（既定5MiB）以内。実データのサイズとSHA-256も照合する。
- HTMLの入口が必要。空の一覧、形式の違うhash、宣言と異なるファイルを受け付けない。

新方式の開始時にはZIPをWorkerへ渡さない。既存の生成物は送信元で展開するため、ZIP全体の展開負荷をWorkerから外せる。

## 4. 作成前にDrive IDを保存する

Google Driveの `files.generateIds` で、一覧の件数分のIDを一度に確保する。
更新の記録と全 `upload_objects` を、少数のSQL文による一つのD1 transactionで保存する。
多数の行の挿入には `json_each(?)` を使い、ファイル数と同じ数のSQL文を発行しない。
この保存が成功してから、実際のファイル作成を始める。

Driveへの作成は、POSTのmetadataに事前IDを指定する。既存のファイル更新に使うPATCHとは区別する。
R2の保存先も更新IDとpathから固定する。同じファイルの再送では、同じDrive IDとR2保存先を使う。

- 完了済みのファイルは、送信データとの一致を確認して保存結果を返し、外部へ再送しない。
- Drive作成の応答が途絶えた場合も、同じIDでPOSTを再送する。Googleが409を返したら、既存実体の照合へ進む。
- 409だけでは保存成功と扱わない。ID・共有ドライブ・親フォルダ・操作識別子・未削除・サイズ・SHA-256を照合する。
- GoogleのSHA-256が取得できない場合は、上限内の実データを取得して照合する。取得失敗や内容不一致では、成功登録へ進まない。
- Driveへの保存と内容一致を確認し、R2保存に成功した後だけ `upload_parts` に登録する。保存失敗時は再送可能な状態を残す。

同じ開始要求が並行して届いた場合は、プロジェクト・送信者・要求IDの一意制約で一つだけ採用する。
競合に負けた要求で確保した未使用のDrive IDには、ファイル実体を作らない。
新規フォルダも事前IDを使い、作成前に既存の `drive_cleanup_folders` へ記録するため、応答が途絶えてもIDを指定して照合できる。

## 5. D1へ追加する情報

| 保存先 | 追加する情報 | 役割 |
|---|---|---|
| `projects` | 準備中の保存先・元の保存先、サービスアカウント、確認済みファイルID、採用したフォルダの親と操作識別子 | 既存の切替ID・期限と合わせて準備を再開する |
| `project_revisions` | 送信ファイル一覧、15分の固定期限、保存先、サービスアカウント | 既存の要求ID・送信者・開始時公開版と合わせて、未公開の更新を記録する |
| `upload_objects` | 削除を再試行する時刻、旧方式の検索位置、新方式の操作識別子 | 既存のDrive ID・R2保存先を、作成前から追跡する |
| `upload_parts`（新規） | 更新ID、path、object ID、Drive更新時刻、R2 etag | 両保存先への保存に成功したファイルだけを記録する |
| `drive_cleanup_folders` | 新規作成時の親フォルダと操作識別子、削除を再試行する時刻 | 作成前のフォルダIDと指定された保存範囲を追跡する |

`project_revisions.published_at IS NULL` を未公開状態として使う。別の送信ジョブ表や汎用ジョブ基盤は作らない。
`upload_parts` は `(revision_id, path)` を一意にする。Drive IDとR2 keyは、開始時に記録した値から変更しない。

## 6. 全件が揃った時だけ公開する

公開の確定では、次の条件を同じD1 transactionの条件付き更新へ含める。

- 全ての送信ファイルが保存済みである。
- 開始から15分以内である。再送で期限を延ばさない。
- 保存先のフォルダとサービスアカウントが開始時と同じである。
- 現在の公開版が開始時と同じである。
- アップロード専用キーが有効、またはユーザー・APIキー・プロジェクト権限が現在も有効である。

条件が揃った場合にだけ、現在のファイル一覧を削除対象として記録し、公開ポインタ・ファイル一覧・成功履歴・保存済み応答をまとめて更新する。
途中のSQLが失敗したら、全体を巻き戻す。GoogleとR2への通信は、このtransactionに含めない。
並行する別の更新が先に公開された場合は409を返し、先に成功した公開版を保持する。

完了要求の再送は保存済み応答を返し、履歴や公開版を増やさない。
成功した要求は同じ結果、期限切れの未公開要求は410、同じ要求IDで違う内容は409として扱う。
要求ID・内容hash・期限・成功結果は保持し、未使用ファイルの削除によって期限切れ要求を新規要求へ戻さない。

## 7. 途中で失敗した場合

| 失敗 | 残る状態 | 次の動作 |
|---|---|---|
| 準備中の通信失敗 | 直前の確認位置 | 同じ切替の有効期限内なら続きを確認する |
| 準備の期限切れ・保存先変更 | 確認位置は再利用不可 | 最新の対象で準備をやり直す |
| 開始応答の消失 | D1に更新がある、または何も登録されていない | 同じ要求IDと一覧で開始し直す |
| Drive作成の応答消失 | 事前IDがD1に保存済み | 同じIDへの作成と実体照合を行う |
| Drive成功後のR2失敗 | Drive IDは既知、送信完了は未登録 | 同じファイルを再送し、両保存先の完了を確かめる |
| キー取消・権限喪失 | 現在の公開版を保持 | 新しい外部書込みと公開を拒否する。未使用実体は後で削除する |
| 並行更新が先に公開 | 自分の更新は未公開 | 409を返す。送信元は最新mainと公開版を確認して新しい要求を開始する |
| 公開確定応答の消失 | D1に成功結果が保存済み | 同じ要求IDで成功結果を取得する |
| 送信の期限切れ | 現在の公開版を保持 | 410を返し、未使用実体を後で削除する |

本文読取り後、外部書込み前、送信成功の登録時、公開確定時に必要な期限・認可を確認する。
外部通信中に権限が取り消された場合、既に送信した実体をなかったことにはできないが、公開と新しい処理への進行は止める。

## 8. 未使用ファイルの削除もFree内に収める

一時間の猶予期間を保ち、公開中のファイルと使用中のフォルダを除外する。新方式の実体は削除直前にも操作識別子・保存先・現在の参照を照合し、不一致なら削除せず追跡を保持する。409の照合で拒否した実体も、この条件を満たさずに削除しない。操作識別子を持たない旧ファイルは、既存の管理情報と現在の参照によって扱う。
ファイルとフォルダを合計5件まで処理する。一件の所在検索は一ページ・一件までとし、残りがあれば追跡行を残す。
旧方式のID未確定レコードだけは既存の操作識別子検索を使う。新方式は作成前からIDが分かるため、この検索を必要としない。

tokenの取得・401後の一度の再試行・所在検索を含め、一件の最大通信数を8回、全体を40回以下とする。
失敗した対象には再試行時刻を設定し、他の対象を先に処理できるようにする。
残りがある追跡行や、使用中の実体を削除しない。旧検索で使用中の結果が先頭にある場合は、次ページの位置を保存して先へ進む。

定期実行の開始値は1分ごとに最大5件（最大300件/時）。83ファイルの全置換を毎時行う場合の削除量を上回る。
待ち件数・最古の作成時刻・失敗後の再試行時刻をD1から確認できるよう、運用手順に読取SQLを残す。
実測CPUがFreeの制限を超える場合は件数を調整し、調整後の処理量も確認する。処理量を超える更新頻度まで保証しない。

## 9. 互換性と配備順序

- `stage` がない既存APIは、既存の単一ファイル・ZIPの応答と認可を保持する。新方式の未公開記録を成功結果と誤認しない。
- キー発行は準備中の202だけを追加する。新しい所有者画面は202を処理し、201で初めて秘密キーを表示する。
- 新方式の開始・ファイル送信・公開確定は、既存のアップロード専用キーの許可範囲内で行う。
- マイグレーションは列・表の追加とし、既存の公開情報・履歴・キーを削除しない。
- 公開アプリの検査とCI → 非公開運用リポジトリの自動配備 → 本番キー発行 → 記事送信元のmain統合、の順に反映する。
- 問題時は分割送信の新規開始を止め、既存の公開版を維持する。未完了の記録を削除して新規要求へ偽装しない。

## 10. 実装を受け入れる条件

1. 93件の既存ファイル確認を複数回で完了し、各実行の外部通信が50回以下、D1のSQLが50件以下である。
2. 83ファイルの送信、中断後の再開、同じ要求の再送、並行要求、キー失効、保存失敗で、公開版と履歴が意図した状態になる。
3. 最大128KiBの一覧、200ファイル、最大5MiBの一件の送信、token更新、409後の内容照合、削除処理のCPU時間をWorkersで測定する。小分けにしたことだけで10ms以内と断定しない。
4. 実Google接続で事前IDによる作成・409後の照合を確認する。モックだけを外部仕様の成功証拠にしない。
5. 所有者画面で準備中の表示からキー発行まで進める。記事送信元のmainへの統合後、同じ公開URLで内容・リンク・閲覧権限・コメントを確認する。
6. 失敗・期限切れの実体を少数ずつ削除でき、使用中の実体・成功履歴・要求IDの判定情報を保持する。
